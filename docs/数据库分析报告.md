# 数据库分析报告

> 分析对象：对标 MES 项目（MesServer）的两个交付物
>
> - `reference/mes-local-pilot.db` — 本地试点 SQLite 数据库快照（含真实试点数据）
> - `reference/mes-mysql-script.zip` — MySQL 版自包含部署包（MesServer.Api，win-x64）
>
> 分析日期：2026-11-08

---

## 1. 对标系统概况

### 1.1 技术栈

| 项 | 内容 |
|---|---|
| 应用 | MesServer.Api（ASP.NET Core 8 发布包，自包含 win-x64） |
| ORM | **EF Core 8.0.4**（数据库由迁移生成，无手写 SQL 脚本） |
| 持久化 | 多 Provider 可切换：`SqlServer` / `MySql`(8.0) / `Sqlite` / `LocalDb` |
| 缓存 | Redis（MySQL 脚本包强制降级为 Memory，免 Redis 依赖） |
| 实时通信 | SignalR（心跳 10s / 客户端超时 60s） |
| 其他 | JWT 认证、Serilog 日志、PLC 轮询/下发后台服务、Ollama 本地 AI 助手 |

### 1.2 两个交付物的关系

- **mes-mysql-script.zip** 不是 SQL 脚本，而是整站发布包。`README.txt` 明确说明："It uses MySQL. No SQLite database file is included"，由 `start.bat` 通过 `MES_*` 环境变量强制 `Persistence.Provider=MySql`。建库依赖应用启动时的 EF Core 迁移。
- **mes-local-pilot.db** 是同一套 schema 在 Sqlite Provider 下的试点运行产物（连接串 `Data Source=mes-local-pilot.db`），可用于离线分析完整的表结构与索引设计。

> **结论：分析 SQLite 快照的 schema 即等同于分析 MySQL 版的目标 schema**（EF Core 多 Provider 共用一套模型，仅类型映射有差异）。

## 3. 设计特点分析

### 3.1 值得借鉴的设计

1. **快照字段（Snapshot）模式**
   `ParamRecords` 存 `ParamCodeSnapshot/ParamNameSnapshot/Lower/Upper/Target/SpecVersionSnapshot`——记录发生时点的规格副本。即使后续 ParameterSpecs 改版，历史判定依据仍可追溯。这是工业追溯系统的关键实践。

2. **规格版本管理**
   `ParameterSpecs` 用 `Version + Status + PublishedAt` 做版本化，参数记录通过 `SpecVersionSnapshot` 锚定版本。

3. **RowNo 自增辅助列**
   ExecutionRecords、ParamRecords、SerialNumbers、StationSessions、WorkOrders 等大表均有 `"RowNo" INTEGER` 列（迁移后期补加）。TEXT 主键（GUID）无序，RowNo 提供稳定的插入顺序用于分页/增量同步。

4. **通用作用域设计**
   `QualityHoldRecords(ScopeType+ScopeId)`、`ExceptionEvents(CorrelationKey)`、`SystemParameters(Key+ScopeType+ScopeId)`——一套结构冻结/记录任意层级对象（工单/批次/SN/工位），避免为每种对象建表。

5. **状态机字段组**
   工单：`CreatedAt/StartedAt/ActivatedAt/CancelledAt/CompletedAt/IsArchived/ArchivedAt`；异常：`AcknowledgedBy/At → EscalatedBy/At → ClosedBy/At`；NC：`AssignedTo → ReviewedBy/At → ClosedBy/At`。双人/三段时间戳齐全，满足审计要求。

6. **索引命名与覆盖规范**
   全部 `IX_{Table}_{Columns}` 风格，高频查询建复合索引（如 `IX_ExceptionEvents_Line_Status_Severity`、`IX_ParamRecords_Execution_Param`、`IX_InspectionTasks_Sn_Status`），外键几乎都有索引。

7. **下发队列表**
   `PlcDispatchJobs` 把 PLC 下发做成持久化队列（状态+重试+下次重试时间），而非内存 fire-and-forget，崩溃可恢复。

8. **删改策略区分**：主数据引用用 `ON DELETE RESTRICT`（防误删），聚合子表用 `CASCADE`（BomItems 随 Boms 删除）。

### 3.2 潜在问题 / 风险点

| 问题 | 说明 |
|---|---|
| **decimal 存为 TEXT** | SQLite 下 EF Core 把 decimal 映射为 TEXT（Quantity、SafetyStock、上下限、ValueDecimal 等全是 TEXT）。数值比较/排序依赖应用层转换，SQL 层无法直接做范围查询；MySQL 版会映射为原生 decimal，**两库行为存在隐式差异风险** |
| **主键全为 TEXT(GUID)** | 无聚簇递增主键，大表（ParamRecords 33 万）插入易产生页分裂（MySQL/InnoDB 下尤其明显），RowNo 是事后补救 |
| **大量空表** | 73 表中约 25 张 0 行（缺陷、首件、质控计划、排产、发料等模块试点未启用），schema 超前于实际使用，维护成本高 |
| **配置内含敏感信息** | appsettings.Development.json 含明文 BootstrapAdmin 密码与 JWT 签名密钥；appsettings.json 中 SigningKey 占位符外还有正式注释提示，部署包 start.bat 生成临时密钥——试点可接受，正式环境需外部化密钥管理 |
| **无分区/归档策略** | ParamRecords、SystemEventLogs、CodeGenerationRecords 持续增长无 TTL/归档设计 |
| **迁移命名不一致** | 69 个迁移中混入了 `20260327014929_20260327121000_AddExceptionEvents` 这类双时间戳命名，反映多人并行开发时迁移管理曾失控 |

## 4. 迁移历史（演进脉络）

`__EFMigrationsHistory` 共 **69 个迁移**，EF Core 8.0.4，时间跨度 2026-02-08 → 2026-08-26：

| 阶段 | 时间 | 标志性迁移 |
|---|---|---|
| 初始建模 | 2026-02 | InitialCreate、工单/产品重构 |
| 一期闭环 | 2026-03 中 | BOM 模块、Phase1ClosedLoop、设备型号/绑定、PLC 编码规则与 IO 点位、StationSessions |
| 试点加固 | 2026-03 下 | PilotHardening、工单激活与配方、下发改重试、角色权限、返工、首件、质控计划、异常事件、排产与质量门禁 |
| 二期扩展 | 2026-04~05 | 物料绑定、产线下发策略、超产标记、虚拟码、IO 点位作用域、工单归档、参数规格改名、返工策略 |
| 三期深化 | 2026-06~08 | 尾站出货码、数据字典、科学计数法、包装管理、原材料批次码、非线性路线、工序角色/喂料、NC 出库检验、产线互斥、**MBOM 生成**、SN 来源追溯、跨工单序列号、物料转移锁 |

最后一个月（2026-08）集中做了 17 个迁移，主题是与上游系统（EBOM→MBOM、跨工单流转）的集成，说明系统正从"单机过站追溯"向"多系统协同"演进。

## 5. 对 CameraTinyMES 的对比与启示

| 维度 | 对标项目（MesServer） | CameraTinyMES 现状 | 启示 |
|---|---|---|---|
| 定位 | 全厂级 MES（工单/BOM/路线/质量/PLC 全链路） | 相机数据轻量采集（samples/images 两表） | 定位不同，**不应照搬全量 schema** |
| 参数记录 | ParamRecords 带**规格快照 + 版本号** | samples 仅存 value/result，无判定依据快照 | **建议采纳**：samples 增加 `lower_limit/upper_limit/spec_version` 快照列，阈值改判历史仍可追溯 |
| 主键 | TEXT GUID（分布式友好，但无序） | INTEGER 自增 | 单机场景自增更优，保持现状 |
| 数值存储 | decimal→TEXT（EF SQLite 局限） | REAL 原生存储 | CameraTinyMES 直接用 SQLAlchemy/原生 SQL，无此问题 |
| 判定模式 | ParameterSpecs 版本化 + JudgementMode | 上下限硬编码在单元格配置 | 中期可引入"规格版本"概念 |
| 事件追溯 | ExceptionEvents（CorrelationKey + 三段处理） | 无 | 相机断线/超差可建轻量 events 表 |
| 图像 | 未涉及（对接 PLC 为主） | images 表 + A0 渲染合成 | CameraTinyMES 的差异化能力，对标项目缺失 |
| 部署 | 多 Provider（SqlServer/MySQL/SQLite） | SQLite 单文件 | 单机 SQLite 足够；若未来多客户端汇聚，可参考其 Provider 抽象 |

**优先级建议**（投入产出比排序）：

1. samples 表增加阈值快照列（低成本、高追溯价值）
2. 增加轻量异常/事件表记录断线与 NG 突发（对应 ExceptionEvents 的简化版）
3. 规格版本字段预留（对应 ParameterSpecs.Version）

## 6. 附：关键表 DDL 摘录

### ParamRecords（对标项目最大表，快照模式范例）

```sql
CREATE TABLE "ParamRecords" (
    "Id" TEXT NOT NULL CONSTRAINT "PK_ParamRecords" PRIMARY KEY,
    "ExecutionRecordId" TEXT NOT NULL,
    "ParamDefId" TEXT NOT NULL,
    "ParamCodeSnapshot" TEXT NOT NULL,      -- 快照：参数编码
    "ParamNameSnapshot" TEXT NOT NULL,      -- 快照：参数名
    "UnitSnapshot" TEXT NULL,
    "ValueDecimal" TEXT NULL,               -- 实测值（decimal 存 TEXT）
    "ValueText" TEXT NULL,
    "JudgeResult" TEXT NOT NULL,            -- OK/NG
    "LowerSnapshot" TEXT NULL,              -- 快照：判定下限
    "UpperSnapshot" TEXT NULL,              -- 快照：判定上限
    "TargetSnapshot" TEXT NULL,
    "SpecVersionSnapshot" INTEGER NOT NULL, -- 快照：规格版本
    "RecordedAt" TEXT NOT NULL,
    "DeviceTimestamp" TEXT NULL, "RowNo" INTEGER,  -- RowNo：后补的递增列
    CONSTRAINT "FK_ParamRecords_ExecutionRecords_ExecutionRecordId"
        FOREIGN KEY ("ExecutionRecordId") REFERENCES "ExecutionRecords" ("Id") ON DELETE CASCADE,
    CONSTRAINT "FK_ParamRecords_ParameterDefinitions_ParamDefId"
        FOREIGN KEY ("ParamDefId") REFERENCES "ParameterDefinitions" ("Id") ON DELETE RESTRICT
);
-- 索引：IX_ParamRecords_Execution_Param (ExecutionRecordId, ParamDefId)、IX_ParamRecords_ParamDefId
```

## 7. 结论

对标项目是一套**架构成熟、演进活跃**（8 个月 69 次迁移）的工厂级 MES：EF Core 多 Provider 设计使同一 schema 可跑在 SQLite（试点）与 MySQL/SqlServer（正式）上；其参数快照、规格版本、持久化下发队列、通用作用域冻结等模式对 CameraTinyMES 有直接借鉴价值。但其 73 表的复杂度远超 CameraTinyMES"相机采集+判定+报表"的定位，**建议仅吸收"快照追溯"与"事件记录"两个核心模式**，保持当前的轻量架构。
