# 相机渲染行为分析报告

- 分析对象：CameraTinyMES 结果渲染（`src/cameratinymes/images.py` + `renderer.py`）
- 对照实现：CameraHelperJimJack（C# / GDI+）、相机自带 Web HMI（浏览器）
- 测试相机：192.168.10.55、192.168.10.145、192.168.10.146
- 测试脚本：`tests/render_compare/run_compare.py`、`tests/render_compare/measure_text_size.py`
- 产物目录：`tests/render_compare/out/`

---

## 一、结论摘要

线上现象是「渲染图里图形缺失，只剩文本，而且文本又小又糊」。本次用三台真机 + 三方渲染实现交叉验证，确认这是**四个独立缺陷叠加**，不是单一原因：

| # | 缺陷 | 位置 | 现象 |
|---|---|---|---|
| 1 | 输出宽度被硬编码为 640（原图 1920 宽，只输出 1/3 分辨率） | `images.py:30` | 文本折算后只有 8px 高，中文糊成一团 |
| 2 | 字号换算系数取 1.333（当作 pt→px），比相机 HMI 实际小 44% | `renderer.py:144`、`images.py:251` | 即使把宽度提到 1920，字仍只有 HMI 的 0.56 倍 |
| 3 | `CompositeRegion` 的子图形没有取 `sub["shape"]` | `renderer.py:234-239` | 圆、矩形等区域图形整体丢失，只剩 Text/Line |
| 4 | 图形坐标越界时没有做视口变换 | `renderer.py:264` | .145 有一个区域坐标 x=2188 > 视口 1920，被画到画布外 |

其中 #3 只在「相机 SVGLayer 不可用、回退到 GraphicsLayer JSON」时触发，这与现场「有时缺图形、有时正常」的表现完全吻合：SVGLayer 可用时图形正确，只是小；一旦回退，图形就消失。

## 二、取图与渲染链路

### 2.1 本软件

```
CogSocket openSession
  → HmiResult.acqImageView.layers
      ├ ImageLayer.url      → 原始图（BMP，可用 ?sz= 缩放）
      ├ SVGLayer.url        → 相机原生 SVG（与 HMI 显示一致）
      └ GraphicsLayer.url   → 图形 JSON 数组
  → images.resolve_sources()
  → images.compose_render()
      ├ 优先：SVG + 底图 → WebView2 Canvas 合成 → JPEG
      └ 兜底：Pillow 逐图形手绘（无 WebView 或渲染失败）
```

关键约束：图层 URL 只在 HMI 会话存活期间有效，会话关闭后 HTTP GET 返回 404，所以抓图层必须在会话内完成。

### 2.2 CameraHelperJimJack

```
CvsInSight.Connect → HmiSessionInfo(IncludeCustomView=true)
  → GetMainImage()       拿到原图
  → GetGraphicsAsync()   拿到 CvsCogShape[]（SDK 已反序列化并做坐标校准）
  → Bitmap(ViewPort.Width/2, ViewPort.Height/2)
  → GraphicsHelper.DrawGraphics(g, Shapes, DisplayContext(usesXY, 0.5f, 0,0, bounds), true)
```

即「视口一半尺寸 + 缩放系数 0.5」，由 SDK 负责坐标系与字号，本软件没有这层 SDK。

### 2.3 相机 Web HMI

浏览器直接访问，无需登录（未开启强制登录）：

```
http://192.168.10.146/?page=ImageAndGraphics&fit=true
http://192.168.10.145/?page=ImageAndGraphics&fit=true
```

其渲染结果就是操作工在现场屏幕上看到的效果，因此**本报告的基准取 HMI，而不是 JimJack**。

## 三、图形完整性对照

同一帧的 GraphicsLayer JSON，经 `renderer.graphics_to_svg()` 转换后的元素统计：

| 相机 | 视口 | 顶层图形 | 生成 SVG 元素 | 丢失内容 |
|---|---|---|---|---|
| .55 | 1964×1503 | 9 Text + 10 Point | text 9、circle 10 | 无 |
| .145 | 1920×1080 | 9 Text + 2 CompositeRegion(Region) + 1 Cross | text 9、line 2、**rect 0** | 2 个矩形检测区域 |
| .146 | 1920×1080 | 5 Text + 1 CompositeRegion(Circle) + 1 Line | text 5、line 1、**circle 0** | 红色定位圆 |

`.146` 的 CompositeRegion 结构：

```json
{ "$type": "CompositeRegion",
  "subregions": [
    { "shape": { "$type": "Circle", "x": 1010.78, "y": 554.07, "radius": 289.07,
                 "color": -65536, "lineThickness": 2 } }
  ] }
```

而 `renderer.py:234-239` 把 `subregions` 里的**包装对象**直接递归，包装对象本身没有 `$type`，于是走到「未知类型」分支后返回空串：

```python
if kind in ("CompositeRegion", "MultiGraphics"):
    out = []
    for sub in (graphic.get("subregions") or []) + (graphic.get("graphics") or []):
        if isinstance(sub, dict):
            out.append(_graphic_svg(sub, color, width))   # ← 应传 sub["shape"]
    return "".join(out)
```

对照 `images.py:281-286` 的 Pillow 实现是正确的（取了 `sub["shape"]`），所以同一份数据走 Pillow 兜底反而能画出圆——两条渲染路径的行为不一致，是排查时最容易误判的地方。

实测图：

- SVG 路径（相机原生 SVGLayer）：圆、线、文字齐全，仅字号偏小
  `tests/render_compare/out/cam146/frame_1/ctm_svg.jpg`
- Graphics 路径：圆完全消失，只剩 5 行文字
  `tests/render_compare/out/cam146/frame_1/ctm_graphics.jpg`

## 四、文本尺寸实测

### 4.1 标定方法

浏览器截图的可视比例取决于窗口大小，不能直接比较像素高度。用画面中一个已知尺寸的图形作为比例尺：

- `.146`：CompositeRegion 中的红圆，`radius = 289.067` → 直径 578.13（视口单位）；截图中实测 312px → 显示倍率 **0.540×**
- `.145`：CompositeRegion 中的绿色区域，`w = 700.909`；截图中实测 374px → 显示倍率 **0.534×**

文字统一量「时间戳行」（`fontSize = 25`）的绿色像素行带高度（纯色阈值，剔除画面亮部噪点）。

### 4.2 测量结果

| 相机 | 来源 | 显示倍率 | 文字实测 | 折算原生(1920) | **折算到 640 宽** |
|---|---|---|---|---|---|
| .146 | 相机 HMI | 0.540× | 23 px | 42.6 px | **14.2 px** |
| .146 | 本软件（640 宽） | 0.333× | 8 px | 24.0 px | **8.0 px** |
| .146 | JimJack（960 宽） | 0.500× | 46 px | 92.0 px | **30.7 px** |
| .145 | 相机 HMI | 0.534× | 23 px | 43.1 px | **14.4 px** |
| .145 | 本软件（640 宽） | 0.333× | 8 px | 24.0 px | **8.0 px** |
| .145 | JimJack（960 宽） | 0.500× | 44 px | 88.0 px | **29.3 px** |

两台相机结论一致（偏差 < 5%）：

| 对比 | 倍数 |
|---|---|
| 本软件 / 相机 HMI | **0.56×** |
| JimJack / 相机 HMI | **2.05×** |
| JimJack / 本软件 | **3.7×** |

### 4.3 字号换算的偏差

以 `fontSize = 25` 反推每套实现的实际放大系数（文字墨迹高度 / fontSize）：

| 实现 | 原生墨迹 | ≈ fontSize × | 代码依据 |
|---|---|---|---|
| 相机 HMI | 42.6 | **1.72** | 相机自身渲染 |
| 本软件 | 24.0 | **0.96** | `fontSize * 1.333` 后再按画幅缩放 |
| JimJack | 92.0 | **3.68** | SDK + `scaleFactor 0.5` |

即：本软件把 fontSize 当 pt 处理（×1.333）仍偏小，相机实际是按约 1.7 倍渲染。要让本地渲染与 HMI 一致，系数需要从 1.333 提到 **约 2.3**（1.333 × 1.72 ≈ 2.29）。

JimJack 的字比 HMI 大了一倍，说明它并不是「与相机屏显一致」的基准，只是字大所以看起来清楚，不能直接拿它的字号当修复目标。

## 五、根因逐条说明

### 5.1 分辨率被压到 640

`images.py:30` `IMAGE_MAX_WIDTH = 640`，`images.py:362` 先 `to_jpeg(data)` 把底图缩到 640，随后 `graphics_to_svg(..., width, height)` 又把 SVG 的 `width/height` 写成 640，`viewBox` 仍是 1920 坐标系 —— 所有图形和文字被等比缩到 1/3。

对 1920×1080 的画面，640 宽意味着 25 号字只有 8px 高，中文笔画必然粘连。

### 5.2 字号系数偏小

`renderer.py:144`：

```python
size = max(9.0, _f(graphic.get("fontSize") or 9) * 1.333)
```

`images.py:251` 的 Pillow 路径同样用 `* 1.333 * k`。实测相机 HMI 的实际倍率是 1.72 倍 fontSize，两者相差 1.79 倍。

### 5.3 CompositeRegion 只丢一层包装

见 3 节。影响面：所有把检测框/定位圆包在 CompositeRegion 里的作业。特征是「有十字线、有文字，但没有外框/圆」。

补充：`_bbox()`（`renderer.py:95-129`）同样对 `subregions` 只取包装对象自身的 `x/y/w/h`，所以这些图形连「兜底虚线框」也画不出来；`graphics_bounds()`（`renderer.py:250`）因此算出的坐标包围盒偏小，`pick_view_size()` 可能误判坐标空间。

### 5.4 坐标越界无处理

`.145` 的两个区域：一个在 `(542.7, 163.6, 700.9, 720)`，正常落在视口内；另一个在 `(2188.1, 1731.5, 327.1, 177.0)`，已经超出 1920×1080 视口。

本软件按像素直接绘制，越界图形被裁掉且无提示；JimJack 因为走 SDK 的 `GraphicsHelper` + `usesXYCoordinates` 校准，会被变换到可见区域。三台相机 `usesXYCoordinates` 都是 true，而本软件完全没有使用该标志。

### 5.5 渲染路径的优先级放大了问题

`compose_render()` 先用相机 SVGLayer（正确），拿不到才用 GraphicsLayer（第 3 条有 bug）。因此现场表现是偶发的：网络抖动、会话超时、图层下载失败时图形就消失，而看起来又像是「随机」的。

## 七、修复建议

按收益排序，P0 两条即可解决 90% 的现场观感问题。

| 优先级 | 修改点 | 建议做法 | 验收标准 |
|---|---|---|---|
| P0 | `renderer.py:234-239` | 子图形取 `sub.get("shape")`，为空再退回 `sub` 本身 | `.145` 生成 `rect=2`、`.146` 生成 `circle=1` |
| P0 | `images.py:30` | `IMAGE_MAX_WIDTH` 提到 960（视口 1/2）或 1920；入库/嵌入 xlsx 的体积需一并评估（640 宽 JPEG 约几十 KB，1920 宽约 4~6 倍） | 输出 960×540，文字墨迹由 8px 提升到 12px（再叠加 P1 可达 21px） |
| P1 | `renderer.py:144`、`images.py:251` | 系数由 1.333 提到 **2.4**（实测相机 HMI 的墨迹高度 ÷ 本模块 em 墨迹比例） | 960 宽输出下文字墨迹 ≈ 21px（与 HMI 同画幅一致）；单独修 P0 只有 12px |
| P2 | `renderer.py:95-129`、`250-261` | `_bbox`/`graphics_bounds` 递归 `sub["shape"]` | 未知类型兜底框不再缺失；`pick_view_size` 判断稳定 |
| P2 | `renderer.py:264` | 对 `usesXYCoordinates=true` 的相机，优先走 SVGLayer；无法取得时按 `GraphicsLayer` 的校准参数或图像偏移做一次坐标变换，越界图形给出日志告警 | `.145` 第二个区域不再静默丢失 |

补充说明：

1. 修 P0 的宽度时注意 `svg_data_url`/`compose_render` 的 `width/height` 与 `viewBox` 必须成对修改，否则图形会二次缩放。
2. 修 P1 后建议以「HMI 截图 vs 本地渲染」的文本折算尺寸作为回归指标（本报告的第四节表格），而不是靠肉眼。
3. 长期方案：优先使用相机 SVGLayer（与 HMI 同源），GraphicsLayer 只做兜底；两端都修好后，兜底路径的图形完整性才可信。
